# Feature Specification: MCP Connection Panel

**Feature Branch**: `007-connection-panel`

**Created**: 2026-08-30

**Status**: Draft

**Input**: User description: "do what we discussed" — a top-bar mascot menu opening a
connection panel: show and copy the MCP endpoint, let the user set the listening port,
optionally require a bearer token, and provide copy-paste snippets (a `claude mcp add`
command, a raw JSON `mcpServers` block) plus a plain-language description of what
HyppoVisor is, so a user or an AI agent can understand and connect to it. HyppoVisor stays
self-sufficient: it exposes MCP and interacts with any page the user opens — no knowledge
of, or UI signs about, job boards or any orchestrator.

## Overview

Today the only in-app trace of the MCP server is one small line at the bottom edge of the
window (`MCP: http://127.0.0.1:7357/mcp`). The port and whether a token is required come
from environment variables (`HYPPO_MCP_PORT`, `HYPPO_MCP_TOKEN`) set before launch; there is
no way to see the full connection details, change the port, turn a token on, or get a
ready-to-paste client configuration from inside the app. A first-time user has nothing that
explains what the app is or how to wire an agent to it.

This feature adds one surface: a **mascot button** in the existing top chrome that opens a
**connection panel**. The panel does four things:

1. **Shows the effective endpoint** and offers copy buttons for it, for a `claude mcp add`
   command, and for a raw JSON `mcpServers` block — each always reflecting the current
   settings so it is valid to paste as-is.
2. **Lets the user set the listening port**, applied without restarting the app, persisted
   across restarts.
3. **Lets the user optionally require a bearer token** — generated by the app, shown
   masked, copyable, regenerable; when on, the server rejects unauthenticated requests and
   every snippet includes the authorization header.
4. **Explains what HyppoVisor is** — a static, copyable description of the app and its MCP
   tool surface, including what it will never do, so it can be pasted to an agent or read by
   a person.

It adds no browser capability and no orchestrator-specific concept. It is configuration and
presentation of the MCP endpoint that already exists.

Boundaries kept from the constitution:

- **The human performs every external act (Principle I).** This feature touches no page and
  adds no interaction primitive. The "what it never does" text restates the boundary
  verbatim from the tool contract (never submits, sends, applies, authenticates, or presses
  Enter).
- **Zero business logic (Principle II).** The panel displays connection facts and static
  text only. No board list, no orchestrator name, no queue, no judgment of any kind. It
  reinforces HyppoVisor's framing as a general authenticated-session MCP server.
- **Solid and comprehensible (Principle III).** One window, one new button, one overlay
  panel. It introduces one small app-local settings file (port / token). The plan MUST
  justify that store as the smallest mechanism that removes the "re-set env vars every
  launch" toil — no service, no daemon, no database, nothing an orchestrator reads.
- **User-held credentials and sessions (Principle IV).** The bearer token here is a
  loopback authorization secret between the app and a local MCP client. It is never a
  website password, never typed into a site, never part of any site's auth. The panel and
  the constitution MUST make that distinction explicit so the token is not mistaken for the
  credentials Principle IV forbids the app from holding.
- **Assistive pace (Principle V).** Unchanged. No page access, no crawling, no pacing
  concern.

## Clarifications

### Session 2026-08-30

- Q: Where should the bearer token be stored at rest? → A: Plaintext in the app-local
  settings file, alongside the port and the token-required flag (one store, one mechanism;
  it only guards a loopback port any local process can already reach).
- Q: When a token is required, do the copyable command / JSON snippets show the real token
  inline or a placeholder? → A: Real token embedded, but the snippet is masked by default
  with the same reveal/copy affordance as the standalone token field — copy still yields
  working text.
- Q: What happens to the existing bottom-edge `MCP: <url>` line once the panel exists? → A:
  Keep it as a compact live status line (effective endpoint + a token indicator when
  required) that opens the panel on click.
- Q: On applying a new port, warn before dropping active connections or rebind immediately?
  → A: Rebind immediately on Apply (no confirm dialog); show a brief inline "now listening
  on <port> — reconnect any agents" notice afterward. Token regenerate keeps its own
  warning.

### Decisions carried by informed default

See Assumptions for the reasoning:

- **Settings persist.** Port and token settings are written to an app-local config file in
  the Electron user-data directory (the same location family as `interaction-log.jsonl`),
  not the shared data directory. Session-only settings were rejected as poor UX.
- **Environment variables win.** `HYPPO_MCP_PORT` / `HYPPO_MCP_TOKEN`, when set, keep their
  current meaning and override the panel; the matching control is shown read-only and
  labelled as environment-controlled.
- **Port change rebinds in place.** Applying a new port re-binds the HTTP listener without
  an app restart; existing MCP connections drop and must reconnect. A port that cannot be
  bound leaves the previous listener running and surfaces an error.
- **`claude mcp add` targets user scope.** The generated command uses user scope (available
  in every project) and the panel says so; the server entry is named `hyppovisor`.
- **stdio mode has no endpoint.** When the app runs under `HYPPO_MCP_STDIO=1` there is no
  HTTP listener; the panel hides the port and token controls and shows stdio connection
  text instead.
- **Constitution gets a one-line PATCH clarification** distinguishing the loopback MCP
  bearer token from site credentials (Principle IV). No principle changes; the token
  mechanism itself already ships.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - See and copy the connection details (Priority: P1)

A user has HyppoVisor running and wants to attach an agent. They click the mascot button in
the top bar. The panel opens showing the endpoint `http://127.0.0.1:7357/mcp`, a
`claude mcp add` command, and a JSON `mcpServers` block. They click "Copy" on the command,
paste it into a terminal, and the agent connects — no editing.

**Why this priority**: This is the MVP. It replaces squinting at an 11px status line with a
real, copy-paste-ready connection surface, and it is independently useful even if the port
and token controls are never touched.

**Independent Test**: With the app at default settings, open the panel; confirm it shows the
correct endpoint URL, a `claude mcp add` command containing that URL and the server name
`hyppovisor`, and a JSON block that parses and contains the same URL; confirm each copy
button places exactly that text on the clipboard.

**Acceptance Scenarios**:

1. **Given** the app is running on the default port with no token, **When** the user opens
   the connection panel, **Then** it displays the endpoint `http://127.0.0.1:7357/mcp`, a
   `claude mcp add --transport http` command for a server named `hyppovisor` at that URL,
   and a JSON `mcpServers` block for the same URL.
2. **Given** the panel is open, **When** the user clicks the copy button on any snippet,
   **Then** the exact displayed text is copied and the button confirms the copy.
3. **Given** the panel is open, **When** the user presses Escape or clicks outside it,
   **Then** the panel closes and the page underneath is unaffected.
4. **Given** the JSON snippet, **When** it is parsed, **Then** it is valid JSON with a
   single `hyppovisor` entry under `mcpServers` pointing at the current endpoint.
5. **Given** the panel is closed, **When** the user clicks the bottom-edge MCP status line,
   **Then** the connection panel opens; the status line always shows the effective endpoint
   and a token indicator when a token is required.

---

### User Story 2 - Set the listening port (Priority: P1)

The default port is taken by another process, or the user simply wants a different one. In
the panel they change the port to `8080` and click Apply. The server starts listening on
`8080`, stops listening on the old port, and every snippet in the panel updates to `8080`.
After quitting and relaunching the app, it is still on `8080`.

**Why this priority**: A fixed, env-only port is a real adoption blocker (port already in
use, corporate policy). In-app, persisted port configuration is the most common reason to
open this panel after the first connect.

**Independent Test**: Open the panel, change the port to a free port, Apply; confirm an MCP
client can reach the new port and cannot reach the old one, that all panel snippets show
the new port, and that the setting survives an app restart.

**Acceptance Scenarios**:

1. **Given** the panel is open and the port field shows `7357`, **When** the user enters a
   free port and clicks Apply, **Then** the server becomes reachable on the new port,
   unreachable on the old port, the panel's endpoint and all snippets show the new port
   (without an app restart), and a brief inline notice names the new port and tells the user
   to reconnect any agents.
2. **Given** a port was applied in the panel, **When** the app is quit and relaunched with
   no `HYPPO_MCP_PORT` set, **Then** the app listens on the previously applied port.
3. **Given** the user enters a port that is already in use or outside the valid range,
   **When** they click Apply, **Then** the change is rejected with a clear message, and the
   server keeps listening on the port it was already using.
4. **Given** `HYPPO_MCP_PORT` is set in the environment, **When** the panel opens, **Then**
   the port field shows that value, is read-only, and is labelled as set by the
   environment.

---

### User Story 3 - Optionally require a bearer token (Priority: P2)

The user wants only authorized clients to reach the local MCP port. In the panel they turn
on "Require token". The app generates a token, shows it masked with a reveal control, and
adds an authorization header to every snippet. Requests without the token are now rejected;
requests with it succeed. Turning the toggle off removes the requirement.

**Why this priority**: Loopback is still reachable by any local process; a token is the
documented hardening step. It is P2 because the default (no token) is a valid posture and
US1/US2 deliver value without it.

**Independent Test**: Toggle "Require token" on; confirm a token is shown (masked until
revealed), all snippets gain the bearer header with that token, an MCP request without the
header is rejected and one with the correct header succeeds; toggle off and confirm requests
without a header succeed again; confirm the choice survives a restart.

**Acceptance Scenarios**:

1. **Given** no token is required, **When** the user turns on "Require token", **Then** the
   app generates a token, the server begins rejecting requests that lack the correct
   `Authorization: Bearer` header, and the panel's command and JSON snippets both include
   that header.
2. **Given** a token is required, **When** the user clicks "Regenerate", **Then** a new
   token replaces the old one, the old token stops working, and the panel warns that
   connected clients must update.
3. **Given** a token is required, **When** the user turns "Require token" off, **Then** the
   stored token is discarded, the server stops requiring a header, and the snippets drop the
   header.
4. **Given** the token is displayed, **When** the panel first renders it, **Then** it is
   masked, and the full value is shown only after the user activates a reveal control or
   copies it.
6. **Given** a token is required, **When** the panel renders the command and JSON snippets,
   **Then** each embeds the real token but is masked by default, and copying a snippet still
   places the working, unedited text on the clipboard.
5. **Given** `HYPPO_MCP_TOKEN` is set in the environment, **When** the panel opens, **Then**
   the token state is shown as environment-controlled and read-only (no toggle, no
   regenerate).

---

### User Story 4 - Understand what HyppoVisor is (Priority: P2)

A user unfamiliar with the app, or one who wants to brief an agent, opens the panel and
reads a short plain-language description: what the app is, what the MCP tools do, and what it
will never do. A copy button puts that text on the clipboard so it can be pasted into an
agent's context.

**Why this priority**: The connection details are useless to someone who does not know what
they are connecting to. This is what makes the panel a self-sufficient "here is the app"
surface. P2 because it is static content with no dependency on US1–US3.

**Independent Test**: Open the panel; confirm it contains a description naming the app, the
current MCP tool set, and the never-does guarantees; confirm the copy button copies exactly
that text and that the text contains no secret (no token, no machine-specific path beyond
what a stdio snippet legitimately needs).

**Acceptance Scenarios**:

1. **Given** the panel is open, **When** the user reads the description block, **Then** it
   states in plain language that HyppoVisor is a local app exposing an MCP server over the
   shown endpoint, lists the available MCP tools, and states that it never submits forms,
   sends messages, applies, authenticates, or presses Enter.
2. **Given** the description block, **When** the user clicks its copy button, **Then** the
   exact text is copied.
3. **Given** the description block, **When** it is inspected, **Then** it contains no bearer
   token and no board- or orchestrator-specific terms.
4. **Given** the panel is open, **When** the user views the description section, **Then** it
   also shows the app version and the license (Apache-2.0), and the mascot image — or, while
   the mascot asset is not yet bundled, a text fallback in its place — without any error.

---

### User Story 5 - Confirm a client reached the server (Priority: P3)

After connecting an agent, the user wants to know it worked without switching to the agent.
The panel shows a single line such as "Last request: 4s ago — read_page". If nothing has
connected yet it shows "No requests yet".

**Why this priority**: A quick confidence check that saves a round-trip to the agent. P3
because it is a convenience; the connection either works or the agent reports an error.

**Independent Test**: With the panel open, issue one MCP call from a client; confirm the
panel updates to show a recent timestamp and the tool name; confirm it never shows request
or response content.

**Acceptance Scenarios**:

1. **Given** the panel is open and no client has called, **When** it renders, **Then** it
   shows "No requests yet".
2. **Given** an MCP client makes a call, **When** the panel is open, **Then** it shows the
   time since the last request and the tool name, and nothing about the request's arguments
   or result.
3. **Given** a token is required and a request arrives without it, **When** the panel is
   open, **Then** the rejected attempt is reflected as a rejected request, not as a
   successful tool call.

---

### Edge Cases

- **Port already in use on Apply**: rejected with a message; the previous listener stays
  up; snippets keep the working port.
- **Port outside 1–65535, or a privileged port below 1024**: rejected with a message;
  the panel recommends a port at or above 1024.
- **Non-numeric or empty port field**: Apply is disabled or rejected; nothing changes.
- **`HYPPO_MCP_PORT` or `HYPPO_MCP_TOKEN` set in the environment**: the corresponding
  control is read-only and labelled environment-controlled; the panel still shows correct
  snippets for the effective value.
- **stdio mode (`HYPPO_MCP_STDIO=1`)**: no HTTP endpoint; the panel omits the port and
  token controls, shows "Running in stdio mode — no network endpoint", and provides a stdio
  JSON snippet using the app's resolved runtime paths.
- **Regenerate token while a client is connected**: old token immediately invalid; panel
  warns that connected clients must reconnect with the new token.
- **Turning the token requirement off**: any stored token is discarded, not just hidden.
- **Clipboard unavailable**: the snippet text remains visible and selectable so it can be
  copied manually.
- **App relaunched with an env var newly set (or newly unset)** compared to the last run:
  the effective value follows the precedence rule (env over persisted over default); the
  persisted value is retained but not applied while the env var is present.
- **Applied port equals the current port**: no-op, no listener churn, no error.
- **Panel open while a port change is applied from elsewhere is not possible** — the panel
  is the only in-app control; there is one source of change at a time.
- **Two app instances contending for a port**: pre-existing OS-level behavior; the second
  instance's bind fails at startup as it does today. Not introduced or solved here.

## Requirements *(mandatory)*

### Functional Requirements

#### The connection panel surface

- **FR-001**: The top chrome MUST gain a control (the mascot button) that toggles a
  connection panel. The panel MUST open as an overlay that does not permanently enlarge the
  window chrome, and MUST close on Escape and on a click outside it.
- **FR-001a**: The existing bottom-edge MCP line MUST be retained as a compact live status
  line showing the effective endpoint and a token indicator when a token is required, and
  MUST open the connection panel when clicked. It MUST update whenever the effective state
  changes (port or token).
- **FR-002**: The panel MUST present the **effective** connection state — the values
  actually in force after applying the precedence rule (environment override, then persisted
  setting, then built-in default) — never a stale or pending value as if it were live.
- **FR-003**: The panel MUST contain no job-board, queue, onboarding, or orchestrator
  concept, name, or link. Its content is limited to: the endpoint, the port control, the
  token control, the copy snippets, the static description, and the optional last-request
  line.

#### Endpoint and copy snippets

- **FR-004**: The panel MUST display the effective endpoint URL
  (`http://127.0.0.1:<port>/mcp` for the HTTP transport) with a copy button.
- **FR-005**: The panel MUST provide a copyable `claude mcp add` command that includes the
  HTTP transport flag, the server name `hyppovisor`, the current endpoint URL, and — when a
  token is required — the `Authorization: Bearer <token>` header argument. The command MUST
  target user scope (available in all of that user's projects) and the panel MUST state that
  in plain language.
- **FR-006**: The panel MUST provide a copyable JSON `mcpServers` configuration block for a
  server named `hyppovisor` pointing at the current endpoint, including an authorization
  header entry when and only when a token is required. The block MUST be valid JSON as
  displayed.
- **FR-007**: Every snippet MUST reflect the current settings at the moment it is shown;
  after the port or token changes, the snippets MUST update before they can be copied again.
- **FR-007a**: When a token is required, the command and JSON snippets MUST embed the real
  token value (so a copy is runnable without edits) but MUST render it masked by default,
  revealed only by the same explicit reveal/copy action that governs the standalone token
  display (FR-018).
- **FR-008**: In stdio mode the panel MUST NOT show an HTTP endpoint or the HTTP snippets;
  it MUST instead show a stdio JSON snippet (command, arguments, and the stdio environment
  flag) built from the app's resolved runtime paths.
- **FR-009**: Each copy control MUST copy exactly the displayed text and MUST give visible
  confirmation. If the clipboard cannot be written, the text MUST remain visible and
  selectable.

#### Port configuration

- **FR-010**: The panel MUST let the user set the HTTP listening port and apply it while the
  app is running. On Apply with a bindable port, the server MUST begin listening on the new
  port and stop listening on the previous one, with no app restart and with no confirmation
  dialog. After a successful rebind the panel MUST show a brief inline notice naming the new
  port and telling the user to reconnect any agents.
- **FR-011**: An applied port MUST persist to an app-local settings store and be used on the
  next launch when no `HYPPO_MCP_PORT` environment variable is set.
- **FR-012**: The panel MUST reject a port that is not an integer in 1–65535, and SHOULD
  warn against privileged ports below 1024. A rejected Apply MUST NOT disturb the running
  listener.
- **FR-013**: If the new port cannot be bound (already in use), the app MUST keep serving on
  the port it was already using and MUST report the failure in the panel.
- **FR-014**: When `HYPPO_MCP_PORT` is set, the port control MUST be read-only and labelled
  as environment-controlled; the persisted value MUST be retained but not applied while the
  environment variable is present.
- **FR-015**: Loopback binding MUST be preserved — the server MUST continue to bind only
  `127.0.0.1`, never a routable interface, regardless of the port chosen.

#### Token configuration

- **FR-016**: The panel MUST let the user turn a required bearer token on or off. Turning it
  on MUST generate a token; turning it off MUST discard the stored token.
- **FR-017**: While a token is required, the HTTP server MUST reject any request whose
  `Authorization` header is not `Bearer <token>` and MUST accept requests that carry it —
  matching the behavior the `HYPPO_MCP_TOKEN` environment variable already produces.
- **FR-018**: The token MUST be displayed masked by default; the full value MUST be revealed
  only on an explicit user action (a reveal control or a copy).
- **FR-019**: The panel MUST offer a "Regenerate" action that replaces the token, takes
  effect immediately (old token rejected), and warns that connected clients must update.
- **FR-020**: The token requirement and token value MUST persist to the app-local settings
  store — stored in plaintext in the same file as the port and the token-required flag — and
  apply on the next launch when no `HYPPO_MCP_TOKEN` environment variable is set.
- **FR-021**: When `HYPPO_MCP_TOKEN` is set, the token controls (toggle, regenerate) MUST be
  hidden or disabled and the state shown as environment-controlled; the panel MUST still
  render snippets with the effective header.
- **FR-022**: The token MUST be generated by the app with sufficient entropy to be
  unguessable (reuse the existing token generator). The panel MUST NOT accept a
  user-typed token value.

#### The description text

- **FR-023**: The panel MUST include a static, plain-language description that: names the
  app; states it exposes an MCP server at the shown endpoint on the local machine; lists the
  MCP tools currently available (`open_url`, `list_open_tabs`, `read_page`,
  `read_form_fields`, `navigate`, `interact`, `wait_for_selector`); and states the
  guarantees that it never submits forms, sends messages, applies, connects, authenticates,
  or presses Enter, and that every interaction is logged locally.
- **FR-024**: The description MUST be copyable as a single block and MUST contain no bearer
  token, no board name, and no orchestrator name.
- **FR-024a**: The description section MUST also show the app version, the license
  (Apache-2.0, with a pointer to the bundled `LICENSE`/`NOTICE`), and the HyppoVisor mascot
  image (`src/renderer/mascot.png`, bundled). The version comes from the app's own metadata.
  If the mascot image fails to load the section MUST fall back to text and MUST NOT error.
  The version / license / mascot are section chrome, not part of the copyable description
  block (FR-024).
- **FR-025**: The description's tool list and guarantees MUST be kept consistent with the
  MCP tool contract; a change to the tool set MUST update this text in the same change.

#### Last-request indicator (P3)

- **FR-026**: The panel MAY show a single line reporting the time since the last inbound MCP
  request and the tool name of that request, or "No requests yet". It MUST NOT display
  request arguments or response content, and MUST NOT persist this information.
- **FR-027**: A request rejected for a missing or wrong token MUST be reflected as a
  rejected request, distinct from a successful tool call.

#### Persistence and precedence

- **FR-028**: The app-local settings store MUST live in the Electron user-data directory
  (the same location family as the interaction log), MUST NOT be written to the shared data
  directory, and MUST NOT be required by, or readable as an interface for, any orchestrator.
- **FR-029**: The effective value of the port and of the token state MUST follow one
  precedence order everywhere it is used or displayed: environment variable, then persisted
  setting, then built-in default (`7357`, no token).
- **FR-030**: The settings file MUST be human-readable and safe to delete; a missing or
  unparseable file MUST fall back to defaults without blocking startup.

#### Documentation and constitution

- **FR-031**: The README MUST be updated to present the in-app connection panel as the
  primary way to view the endpoint, set the port, and enable a token, with the environment
  variables documented as the override for headless or scripted launches.
- **FR-032**: `.specify/memory/constitution.md` MUST receive a one-line clarification that
  the loopback MCP bearer token (an app-to-local-client authorization secret) is distinct
  from the website credentials Principle IV bars the app from holding, recorded in the
  amendment history as a PATCH bump (1.3.0 → 1.3.1). No principle is redefined; the token
  mechanism itself already ships via `HYPPO_MCP_TOKEN`.

#### Scope guards

- **FR-033**: This feature MUST NOT change the MCP tool contract, the blocklist, the
  interaction audit log, tab or browser behavior, or the choice of transport made at launch.
- **FR-034**: The server MUST NOT gain any auth scheme beyond the single static bearer
  token, and MUST NOT bind any non-loopback interface or offer remote/TLS access.

### Key Entities

- **Connection settings**: the persisted, user-owned values — listening port; token-required
  flag; token value. Stored app-locally, outside the shared data directory.
- **Effective connection state**: the values actually in force — transport (http or stdio),
  endpoint URL, port, whether a token is required — resolved by precedence (environment,
  then persisted, then default). Read-only, derived.
- **Connection snippet**: a copyable text artifact derived from the effective state — the
  endpoint URL, the `claude mcp add` command, the HTTP JSON `mcpServers` block, or (in stdio
  mode) the stdio JSON block. Always valid as displayed.
- **About text**: a static description of HyppoVisor and its MCP tool surface, including the
  never-does guarantees. Contains no dynamic or secret content.
- **About section chrome**: the app version (from app metadata), the license (Apache-2.0 +
  pointer to `LICENSE`/`NOTICE`), and the mascot image (asset supplied later; text fallback
  meanwhile). Shown around the About text; not part of the copyable block.
- **Last request (optional)**: the timestamp and tool name of the most recent inbound MCP
  request, or a rejected-request marker. In-memory only, metadata only.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user with the app running can connect a fresh agent session using only text
  copied from the panel, with no manual editing, in under one minute.
- **SC-002**: Changing the port in the panel and clicking Apply makes the server reachable
  on the new port and unreachable on the old one within a few seconds, without an app
  restart, 100% of the time when the chosen port is free.
- **SC-003**: A port or token setting chosen in the panel is still in effect after quitting
  and relaunching the app, in 100% of cases where no matching environment variable is set.
- **SC-004**: With a token required, 100% of requests carrying the correct bearer token
  succeed and 100% of requests without it are rejected; with the token off, 100% of
  well-formed requests succeed.
- **SC-005**: The token is never shown in plain text before the user activates a reveal
  control or a copy, in 100% of panel opens.
- **SC-006**: For any combination of current port and token state, the panel's `claude mcp
  add` command runs without edits and its JSON block parses, 100% of the time.
- **SC-007**: When an environment variable sets the port or token, the panel shows the
  effective value and provides no way to edit it, 100% of the time.
- **SC-008**: In stdio mode the panel shows no HTTP endpoint and offers stdio connection
  text instead, 100% of the time.
- **SC-009**: The panel contains zero references to job boards or any orchestrator, verified
  by inspection of all panel text.
- **SC-010**: A rejected Apply (port in use or invalid) never interrupts service on the
  port already in use, in 100% of attempts.

## Assumptions

- **A new mascot button in existing chrome.** The panel is reached from a single new button
  added to the current top strip; it opens as an overlay (closes on Escape / outside click)
  and does not increase the permanent chrome height. No other navigation is added.
- **Settings persist app-locally.** Port and token settings are written to a small
  human-readable file in the Electron user-data directory — the same location family as
  `interaction-log.jsonl`, never the shared data directory. This is a new small persistent
  store; the plan's Constitution Check must justify it under Principle III as the smallest
  mechanism that removes "set the env vars again every launch" toil. It is app
  configuration, not pipeline state, and no orchestrator reads it.
- **Environment variables keep their current meaning and win.** `HYPPO_MCP_PORT` and
  `HYPPO_MCP_TOKEN` behave exactly as today. When either is set, the panel shows the
  effective value read-only; the persisted value is kept for the next launch without the
  override but is not applied meanwhile.
- **Port change rebinds in place.** Applying a port re-binds the loopback HTTP listener
  live. Active MCP connections drop and must reconnect — acceptable because a port change is
  a deliberate, infrequent act. A bind failure leaves the old listener untouched.
- **Single static bearer token, generated by the app.** Reuses the existing token
  generator. Masked display, reveal-on-action, regenerate. No user-supplied token, no
  rotation schedule, no per-client keys. Turning the requirement off discards the token.
- **`claude mcp add` uses user scope.** The command makes the server available in all of the
  user's projects; the panel states this. A user who wants project-only scope can adjust the
  command themselves — the panel does not need a scope selector for v1.
- **stdio mode is presented, not configured.** Transport is fixed at launch. In stdio mode
  the panel is informational: no endpoint, no port/token controls, a stdio JSON snippet
  using the app's resolved runtime paths.
- **The description is static and ships with the app.** It contains no secrets and is
  updated in lockstep with the MCP tool contract. It draws the never-does guarantees from
  the constitution's Principle I and the tool contract.
- **Version / license / mascot are section chrome.** The version is read from app metadata
  (currently `0.1.0`); the license is the fixed string "Apache-2.0" with a pointer to the
  bundled `LICENSE` / `NOTICE`; the mascot is `src/renderer/mascot.png` (HyppoVisor V10
  art, vendored into the repo and copied to `dist/renderer/` at build) — the panel still
  falls back to text if the image fails to load.
- **Last-request indicator is best-effort and metadata-only.** Timestamp and tool name,
  in-memory, never content, never persisted. It can be dropped without affecting US1–US4.
- **Constitution clarification is a PATCH.** The loopback MCP token is not a website
  credential; the one-line note prevents a false Principle IV flag at the review gate. The
  token capability already exists, so nothing new is being blessed — hence PATCH, not MINOR
  (contrast feature 006's clarifying MINOR, which expanded a permitted-action list).
- **No change to the tool surface.** The blocklist, the audit log, the interaction
  primitives, and tab behavior are all untouched.

## Out of Scope

- **Any dashboard, review queue, onboarding checklist, board list, or orchestrator-specific
  UI.** Removing the "two UI surfaces" language from the constitution's preamble/§6.2/§6.3
  is a separate change, not part of this feature.
- **Binding a non-loopback interface, remote access, or TLS/https.**
- **Any authentication scheme beyond one static bearer token** — no OAuth, no per-client
  credentials, no scheduled rotation.
- **Switching transport (HTTP ↔ stdio) at runtime.** Transport stays as launched.
- **Editing other limits from the panel** — text byte caps, wait timeouts, batch caps
  remain environment-only.
- **A persisted or browsable MCP request history** beyond the single optional last-request
  line.
- **Multi-user or multiple named server profiles.**
- **A scope selector for the `claude mcp add` command** (user scope is emitted; the user can
  edit it).
